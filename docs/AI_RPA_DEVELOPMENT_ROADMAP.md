# DDUK ERP AI/RPA 단계별 로드맵

## 문서 목적

- 이 문서는 DDUK ERP 프로젝트에서 `RPA`, `이상 탐지`, `추천 발주`, `ERP 조회형 챗봇`을 어떤 순서로 붙일지 정리한 구현 로드맵이다.
- 이 문서는 아이디어 메모가 아니라 `현재 코드 기준으로 바로 구현 가능한 순서`를 고정하기 위한 계약 문서다.
- 실제 코드 반영 전에는 각 단계별 API, DB, UI 계약을 다시 확인하되, 이 문서의 순서와 제약은 기본 가이드로 사용한다.

> [!IMPORTANT]
> - 회계 대시보드 RPA는 현재 범위에서 제외한다.
> - 현재 기준으로 이미 존재하는 기능과 아직 없는 기능을 명확히 분리한다.
> - 없는 API, 없는 task 분기, 없는 화면 mount를 이미 있는 것처럼 가정하지 않는다.

## 현재 코드 기준 요약

### 이미 있는 것

- `task_history` 저장 구조와 관리자 이력 화면이 있다.
- 백엔드에는 RPA 서버로 요청을 보내는 `RpaClientService`가 있다.
- RPA 서버에는 `/api/v1/rpa/trigger`, `/health`, mock 로그인/수집 흐름이 있다.
- RPA callback 엔드포인트 `/api/v1/callbacks/rpa`가 있다.
- 구매/발주 대시보드, 재고 대시보드, 관리자 시스템 화면은 이미 존재한다.

### 아직 없는 것

- 프론트에서 직접 호출할 `POST /api/v1/admin/rpa/trigger` 백엔드 API가 없다.
- `taskType -> actionName -> script` 공용 분기 체계가 없다.
- RPA 서버는 현재 `collect_purchase_orders` 1개 액션만 사실상 처리한다.
- callback 저장 로직도 현재는 단일 action 기준이다.
- 구매/재고/인사 대시보드에 RPA 결과 위젯을 붙이는 공용 helper가 없다.
- 구매 대시보드에는 `최근 수집 단가 / ERP 기준값 / 차이` 비교 데이터 계약이 아직 없다.

### 현재 구현 제약

- 백엔드 내부 서비스는 현재 단일 액션 `collect_purchase_orders`를 RPA 서버로 전송한다.
- RPA 서버는 어떤 요청이 와도 `purchase_order_task.py`를 실행하는 구조다.
- task history는 `taskType=RPA` 수준 집계는 가능하지만, 여러 시나리오를 안정적으로 구분하는 계약은 아직 없다.
- AI 시연용 데이터를 실제 운영 테이블에 섞어 넣으면 추천/이상탐지 결과를 오염시킬 수 있다.

## 기본 원칙

### 1. 기존 대시보드에 위젯 형태로 붙인다

- 기존 HTML 구조를 갈아엎지 않는다.
- 각 화면에는 `placeholder 1개 + helper JS 1개` 방식으로 붙인다.
- AI/RPA는 기존 CRUD를 대체하지 않고, 조회/수집/비교 보조 기능으로 붙인다.

예시:

```html
<div id="rpa-dashboard-widget" class="mt-6"></div>
<script src="../../services/admin/rpa-dashboard-helper.js"></script>
```

### 2. 공용 기반과 도메인 시나리오를 분리한다

- 먼저 `trigger API`, `task history`, `callback`, `helper JS`, `result widget` 공용 기반을 만든다.
- 그 다음 구매/재고/인사 시나리오를 순서대로 붙인다.
- ERP 데이터 자동 반영이나 자동 발주 같은 쓰기 동작은 조회형 시연 이후로 미룬다.

### 3. 초반에는 조회/수집/비교까지만 간다

- 초기 단계 목표는 `수집`, `저장`, `상태 표시`, `비교 표시`까지다.
- 외부 수집 결과를 ERP 실데이터에 자동 반영하지 않는다.
- 초기 단계에서는 사용자가 결과를 보고 판단할 수 있는 카드/표 중심으로 구성한다.

### 4. 데모 데이터와 운영 데이터는 분리한다

- AI 시연용 합성 데이터는 실제 운영 테이블에 무분별하게 누적하지 않는다.
- 필요하면 별도 seed, 별도 파일, 별도 표기 규칙으로 관리한다.
- 추천/이상탐지 로직이 실운영 테이블을 읽는 경우, 데모 데이터 혼입 방지 규칙을 먼저 고정한다.

## Stage 0. 공용 계약 고정

### 목표

- 현재 코드에 없는 공용 계약을 먼저 명시한다.
- Stage 1 이후 구현이 문서-코드 불일치 없이 진행되도록 준비한다.

### 이번 단계에서 반드시 고정할 계약

1. 백엔드 공개 트리거 엔드포인트 유무와 스키마
2. `taskType -> actionName -> script` 매핑표
3. callback payload 공통 필드
4. 화면별 helper mount 위치
5. task history에 어떤 식별자를 남길지
6. 데모 데이터와 운영 데이터 분리 원칙

### 권장 백엔드 트리거 계약

현재 프론트가 직접 호출할 관리자용 트리거 API가 없으므로, 아래 계약을 Stage 1 선행 조건으로 둔다.

`POST /api/v1/admin/rpa/trigger`

```json
{
  "taskType": "PURCHASE_PRICE"
}
```

응답 예시:

```json
{
  "status": "success",
  "data": {
    "taskId": "rpa-task-001",
    "taskType": "PURCHASE_PRICE",
    "actionName": "collect_purchase_orders",
    "accepted": true
  },
  "message": "RPA trigger accepted"
}
```

### 권장 callback 계약

```json
{
  "taskId": "rpa-task-001",
  "taskType": "PURCHASE_PRICE",
  "actionName": "collect_purchase_orders",
  "status": "success",
  "data": {},
  "error": null
}
```

### 권장 task 매핑표

| taskType | actionName | 초기 script | 비고 |
|---|---|---|---|
| PURCHASE_PRICE | collect_purchase_orders | `rpa/tasks/purchase_order_task.py` | 1차 구현 대상 |
| INVENTORY_SHORTAGE | check_inventory_shortage | 미구현 | Stage 3에서 추가 |
| HR_MIN_WAGE | collect_hr_reference | 미구현 | Stage 5에서 추가 |

### 완료 기준

- 관리자용 trigger 계약이 문서에 명시된다.
- callback에 `taskType`, `actionName`을 포함한다는 규칙이 고정된다.
- task 분기표가 문서에 존재한다.
- 화면 mount 위치와 helper 파일 책임이 명확하다.
- 데모 데이터 분리 원칙이 문서에 박힌다.

## Stage 1. 공용 RPA 흐름 구현

### 목표

- 프론트 버튼 클릭부터 RPA 수락, task history 기록, 결과 조회까지 공용 흐름을 완성한다.

### 구현 작업

1. `frontend/services/admin/rpa-dashboard-helper.js` 생성
2. 현재 페이지/위젯 기준으로 `taskType`을 넘기는 최소 로직 작성
3. 백엔드 `POST /api/v1/admin/rpa/trigger` 구현
4. 백엔드가 `taskType`을 `actionName`으로 변환하도록 분기 추가
5. RPA 서버가 `actionName` 기준으로 script를 고르도록 분기 추가
6. callback 저장 시 `taskType`, `actionName` 구분이 유지되도록 보강
7. 위젯에 `요청됨`, `실행중`, `성공`, `실패` 최소 상태 표시 추가

### 구현 메모

- 현재 `RpaClientService`는 내부 서비스 호출용이므로, 관리자 API를 새로 열거나 기존 구조를 감싸는 controller/service 조합이 필요하다.
- 현재 RPA 서버는 요청 action과 무관하게 `purchase_order_task.py`를 실행하므로, Stage 1에서 최소 분기 테이블이 필요하다.
- task history는 기존 테이블을 재사용하되, 여러 시나리오를 구분할 필드 사용 방식을 문서와 코드에서 맞춘다.

### 완료 기준

- 프론트에서 백엔드 관리자 트리거 API를 호출할 수 있다.
- `taskType`별 최소 분기 구조가 생긴다.
- task history에서 어떤 시나리오 요청인지 구분 가능하다.
- helper JS가 기존 페이지 로직을 망가뜨리지 않는다.

### 지금 하지 않는 것

- 여러 시나리오 동시 완성
- ERP 자동 반영
- 추천/이상탐지 계산

## Stage 2. 구매/발주 대시보드 1차 시나리오

### 목표

- 현재 코드와 가장 가까운 구매/발주 흐름부터 실제 시연 가능한 형태로 완성한다.

### 1차 시나리오

- 특정 공급처 페이지에서 가격/상품 정보를 수집한다.
- 수집 결과를 구매/발주 대시보드의 비교 카드로 보여준다.
- 여기서는 `비교`까지만 하고 자동 발주나 DB 반영은 하지 않는다.

### 1차 대상 업체 계약

- 1차 크롤링 대상은 `아망티`로 고정한다.
- 초기 목적은 `가격/상품 정보 수집`이다.
- 수집 항목은 아래로 제한한다.

| 항목 | 설명 |
|---|---|
| itemName | 상품명 |
| price | 수집 가격 |
| spec | 규격 |
| stockStatus | 재고 여부 |
| productUrl | 상품 URL |
| collectedAt | 수집 시각 |

### 구현 작업

1. `PURCHASE_PRICE` taskType 추가
2. RPA 서버에서 `collect_purchase_orders`를 `PURCHASE_PRICE` 시나리오와 연결
3. 구매/발주 대시보드에 trigger 버튼과 결과 영역 추가
4. 백엔드에 비교 카드용 응답 계약 추가
5. 화면에 아래 3개 값을 표시

- 최근 수집 단가
- ERP 기준값
- 차이

### Stage 2 선행 조건

- 현재 구매 대시보드 API는 발주 통계만 내려주므로, 비교 카드용 별도 API 또는 기존 stats 확장이 필요하다.
- 현재 화면에는 RPA 위젯 mount가 없으므로 helper 삽입 위치를 먼저 정해야 한다.

### 완료 기준

- 구매/발주 대시보드에서 버튼 클릭 시 실제 RPA가 실행된다.
- 수집 결과가 task history에 남는다.
- 대시보드에서 비교 카드가 보인다.
- 수집 결과는 운영 데이터 자동 반영 없이 비교용으로만 사용된다.

## Stage 3. 재고 대시보드 조회형 시나리오

### 목표

- 재고 대시보드에는 부족/공급 관련 조회형 보조 카드만 붙인다.

### 권장 시나리오

- 외부 공급처 또는 공급 페이지에서 공급 가능 정보만 조회한다.
- ERP 재고 부족 항목과 나란히 보여주는 경고 카드 중심으로 구성한다.

### 구현 작업

1. `INVENTORY_SHORTAGE` taskType 추가
2. 재고 대시보드용 helper mount 추가
3. 조회 결과를 경고 카드 형태로 표시

### 주의

- 초기 단계에서는 조회와 표시까지만 한다.
- 자동 입고/자동 재고 조정은 하지 않는다.
- 재고 페이지는 현재 재고 자체 통계에 집중되어 있으므로 RPA 정보는 보조 카드로만 붙인다.

### 완료 기준

- 재고 대시보드에서 조회형 카드가 보인다.
- 기존 재고 통계/차트와 충돌하지 않는다.

## Stage 4. 회계 대시보드 조회형 시나리오

> [!IMPORTANT]
> 이번 작업 범위에서 제외한다.
> 문서에는 기록만 남기고 실제 구현 순서에는 포함하지 않는다.

## Stage 5. 인사/급여 조회형 시나리오

### 목표

- 인사/급여 쪽은 계산 로직 결합 전에 기준 정보 조회 카드부터 붙인다.

### 권장 시나리오

- 최저임금, 가이드, 기준 정보 조회 결과를 보조 카드로 표시한다.

### 구현 작업

1. `HR_MIN_WAGE` taskType 추가
2. 인사/급여 화면에 mount 위치 확정
3. 기준 정보 카드 표시

### 완료 기준

- 인사/급여 화면에서 버튼 클릭 후 기준 정보가 보인다.
- 계산/저장 로직과 직접 결합하지 않는다.

## Stage 6. 운영 UX 보강

### 목표

- 앞 단계에서 붙인 RPA를 운영 가능한 수준으로 다듬는다.

### 구현 작업

1. 최근 실행 이력 목록 보강
2. 실패 메시지 정리
3. 재시도 버튼 추가
4. callback 지연/미도착 상태 표시
5. 실행중 표시 개선

### 완료 기준

- 운영자가 실패 원인을 빠르게 읽을 수 있다.
- 재시도 흐름이 있다.
- 진행중/실패/완료 상태가 명확하다.

## Phase 2. 규칙 기반 이상 탐지 MVP

### 목표

- ML보다 먼저 설명 가능한 규칙 기반 이상 탐지를 붙인다.

### 구현 작업

1. 규칙 기반 이상 탐지 로직
2. 배치 또는 주기 실행 방식 정의
3. `anomaly_logs` 같은 별도 저장 구조 설계
4. 관리자 경고 목록 UI 추가

### 운영 상태

- `OPEN`
- `CONFIRMED`
- `FALSE_POSITIVE`
- `IGNORED`

### 데이터 원칙

- 시연용 이상 거래는 운영 테이블 원본을 더럽히지 않는 방식으로 넣는다.
- 가능하면 별도 seed 또는 별도 demo 표식이 있는 데이터만 사용한다.

## Phase 3. 통계 기반 추천 발주 MVP

### 목표

- 재고/출고/발주 이력을 기반으로 추천 발주 카드를 제공한다.

### fallback 규칙

- 최근 사용 이력이 부족하면 비활성화
- 현재고가 없으면 비활성화 대신 경고 문구 표시
- 리드타임 근거가 없으면 비활성화
- 계산 결과가 비정상이면 `수동 검토 필요` 문구 표시

### 데이터 원칙

- 현재 추천 로직이 운영 테이블을 직접 읽는 만큼, 데모 데이터는 분리된 경로로 관리한다.
- 추천 정확도 실험용 데이터를 운영 발주/재고 집계에 섞지 않는다.

## Phase 4. ERP 조회형 챗봇

### 목표

- 자유 대화보다 먼저 `ERP 조회형` 챗봇을 만든다.
- RAG보다 현재 내부 API 조회 응답을 우선한다.

### fallback 규칙

- 질문 범위가 불명확하면 일반 안내만 반환
- 대응 API가 없으면 지원하지 않는다고 안내
- 권한이 없으면 차단
- 응답 실패 시 재시도 안내

## Phase 5. ML 고도화

### 목표

- 충분한 데이터가 쌓인 뒤에 이상 탐지와 수요 예측 정확도를 높인다.

### 선행 조건

- 누적 이력 데이터 확보
- Phase 2, 3 운영 결과 확보
- 비교 가능한 검증 기준 확보

## 최종 권장 구현 순서

1. 관리자용 RPA trigger 계약을 먼저 만든다.
2. `taskType/actionName/script/callback` 매핑을 먼저 고정한다.
3. 공용 helper와 task history 식별 규칙을 맞춘다.
4. 구매/발주 대시보드부터 실제 시연 가능한 카드형 결과를 붙인다.
5. 재고와 인사는 조회형 보조 카드만 순차 확장한다.
6. 운영 UX를 보강한다.
7. 그 다음에 이상 탐지, 추천 발주, 조회형 챗봇으로 확장한다.
8. ML 고도화는 마지막에 검토한다.

## 최종 판단

- 지금 코드 기준으로 가장 안전한 순서는 `공용 계약 -> 공용 트리거 -> 구매/발주 -> 재고 -> 인사 -> 운영 UX`다.
- 회계 대시보드 RPA는 이번 범위에서 제외한다.
- Stage 0 없이 Stage 2로 바로 가면, 프론트 호출점/백엔드 API/action 분기/callback 식별이 다 어긋날 가능성이 높다.
- 데모 데이터는 운영 테이블과 분리하는 원칙을 먼저 박아두는 게 맞다.
