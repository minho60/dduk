# DDUK ERP AI/RPA 향후 개발 계획

이 문서는 AI 서버와 RPA 서버의 로컬 구동 및 기능 점검이 끝난 뒤, 다음 단계에서 어떤 순서로 개발을 진행할지 정리한 로드맵이다.

현재 기준 상태는 아래와 같다.

- AI 서버 구동 확인 완료
- RPA 서버 구동 확인 완료
- 백엔드 AI 프록시 호출 확인 완료
- RPA trigger / callback 기능 확인 완료
- 주요 실패 시나리오 점검 완료
- AI 한국어 응답 품질 1차 보정 완료
- RPA callback 실패 시 durable logging 보강은 아직 남아 있음

---

## 1. 다음 단계 목표

이제 목표는 `서버가 뜨는지` 확인하는 단계가 아니라, `AI/RPA를 ERP 업무 흐름에 실제로 연결하는 단계`로 옮겨간다.

다음 단계 핵심 목표:

- AI와 RPA의 역할 분리
- 한 개 업무 시나리오를 끝까지 연결
- 실행 이력과 상태 관리 구조 추가
- 최소 운영 화면 추가
- 로그와 재시도 정책 보강

---

## 2. 개발 원칙

앞으로의 개발은 아래 원칙으로 진행하는 것을 권장한다.

- 처음부터 여러 도메인에 확장하지 말고 대표 시나리오 1개를 먼저 닫는다.
- `RPA는 수집`, `AI는 요약/설명` 역할로 분리한다.
- 기능 추가보다 `이력 저장`, `실패 추적`, `운영 확인`을 먼저 붙인다.
- 실제 팀원 작업 상황이 정리되기 전까지는 범용 구조보다 최소 동작 구조를 우선한다.
- UI는 대규모 챗봇 화면보다 관리자 점검/실행 화면부터 시작한다.

---

## 3. 우선순위 제안

### 3-1. 1순위: 대표 업무 시나리오 1개 확정

가장 먼저 할 일은 AI/RPA를 어디 업무에 붙일지 한 줄기를 정하는 것이다.

추천 우선 후보:

- `inventory` 도메인
- 발주 수집 / 발주 검토 / 재고 부족 판단 보조

이 시나리오가 좋은 이유:

- 현재 RPA 예제도 발주 수집 흐름에 가깝다.
- AI 요약 기능과 연결하기 쉽다.
- ERP 핵심 데이터 흐름과도 자연스럽게 이어진다.

권장 확정안:

- RPA가 외부 발주/주문 정보를 수집
- 백엔드가 결과를 저장
- AI가 수집 결과를 한국어로 요약
- 사용자가 관리자 또는 재고 화면에서 결과를 확인

### 3-2. 2순위: 작업 이력 저장 구조 추가

현재 가장 필요한 기반 기능이다.

필수 항목:

- task id
- task type
- caller
- started at / finished at
- status: `queued`, `running`, `success`, `failed`
- error code / error message
- result summary
- raw payload 또는 참조 경로

권장 대상:

- `rpa_task_history`
- `ai_task_history` 또는 공통 task history 구조

이 단계가 먼저 필요한 이유:

- 지금은 기능은 되지만 운영 중 실패 원인을 구조적으로 조회하기 어렵다.
- 이후 UI, 재실행, 장애 대응, 품질 측정이 다 이 구조에 의존한다.

### 3-3. 3순위: RPA callback 실패 관측성 보강

이번 점검에서 남은 가장 중요한 운영 과제다.

현재 문제:

- backend down 시 callback 실패가 durable log로 남지 않는다.
- subprocess stdout/stderr 처리 구조 때문에 사후 추적성이 약하다.

필수 보강:

- callback 실패를 메인 로그에 남기기
- task별 실패 로그 파일 또는 DB 이력 반영
- 재시도 정책 여부 결정

권장 방향:

- 최소한 `taskId`, callback URL, status, error message`는 durable log에 남긴다.

### 3-4. 4순위: 최소 운영 UI 추가

챗봇 UI를 크게 만들기 전에 운영 화면부터 넣는 것이 낫다.

추천 화면:

- AI 테스트 요청 화면
- RPA 실행 버튼
- 최근 실행 이력 목록
- 성공/실패 상태 표시
- 실패 사유 상세 확인
- 수집 결과 미리보기

이 화면의 목적:

- 개발자만 API를 직접 호출하지 않아도 됨
- 팀원들이 기능 상태를 쉽게 검증할 수 있음
- 이후 실제 사용자 기능으로 확장할 수 있음

## 4. 단계별 로드맵

## Phase 1. 기반 안정화

목표:

- 기능은 이미 동작하므로, 운영 가능하게 만드는 기반을 먼저 닫는다.

할 일:

- AI/RPA task history 구조 설계
- callback 실패 durable logging 추가
- AI 요청/응답 로그 최소 정리
- 공통 상태값 정의
- 재시도 여부와 timeout 정책 문서화

완료 기준:

- task id 기준으로 성공/실패 이력 추적 가능
- callback 실패가 로그나 이력에 남음
- 운영자가 최근 실행 결과를 사후 확인할 수 있음

## Phase 2. 대표 시나리오 연결

목표:

- inventory 대표 시나리오 1개를 실제로 끝까지 연결한다.

추천 시나리오:

- `외부 발주 정보 수집 -> 백엔드 저장 -> AI 요약 -> 화면 노출`

할 일:

- RPA 수집 결과를 백엔드 저장 구조와 연결
- 저장 결과를 AI 요약 입력으로 연결
- 백엔드 조회 API 제공
- 최소 화면에서 실행/조회 가능하게 연결

완료 기준:

- 사용자가 버튼 한 번으로 실행 가능
- 실행 결과가 이력에 저장됨
- 요약 결과를 화면에서 확인 가능

## Phase 3. 사용자 기능화

목표:

- 점검용 기능을 실사용 가능한 업무 보조 기능으로 바꾼다.

할 일:

- 도메인별 질문 템플릿 추가
- AI 답변 품질 세분화
- 수집 결과 요약 포맷 개선
- 권한별 접근 통제 점검
- 실패 재실행 UX 추가

완료 기준:

- 관리자/실무자가 개발자 도움 없이 사용 가능
- 반복 점검 없이도 기능 흐름이 안정적임

## Phase 4. 확장

목표:

- 첫 시나리오가 닫힌 뒤 다른 도메인이나 기능으로 확장한다.

확장 후보:

- 재고 부족 자동 판단 보조
- 거래처 주문 수집 확장
- 운영 로그 요약
- 관리자용 AI 질의응답
- 문서/정산 보조

전제 조건:

- Phase 1~3 완료
- 첫 시나리오에서 이력/로그/운영 구조가 검증됨

## 5. 추천 구현 순서

실행 순서를 한 줄로 줄이면 아래와 같다.

1. task history / 상태 저장 구조 추가
2. callback 실패 durable logging 보강
3. inventory 대표 시나리오 확정
4. RPA 수집 결과 백엔드 저장 연결
5. AI 요약 기능 연결
6. 관리자용 최소 실행/조회 UI 추가
7. 재시도/운영 로그 보강
8. 다른 도메인 확장

## 6. 예상 산출물

다음 개발 단계에서 실제로 생겨야 하는 산출물 예시는 아래와 같다.

문서:

- AI/RPA task status 정의 문서
- timeout / retry 정책 정리
- inventory 대표 시나리오 명세

백엔드:

- task history entity / repository / service
- RPA 결과 저장 API
- AI 요약 API 또는 서비스 연계

AI 서버:

- 도메인별 응답 품질 보강
- 질문 템플릿 또는 system instruction 보강

RPA:

- durable failure logging
- callback 재시도 또는 실패 누적 처리

프론트:

- 관리자용 AI/RPA 실행 화면
- 최근 실행 이력 화면
- 결과 상세 화면

## 7. 리스크와 대응

### 리스크 1. 기능을 여러 군데에 동시에 붙이다가 구조가 흩어질 수 있음

대응:

- 대표 시나리오 1개만 먼저 닫는다.

### 리스크 2. 실행은 되는데 운영 추적이 안 될 수 있음

대응:

- task history와 durable logging을 기능 확장보다 먼저 구현한다.

### 리스크 3. AI 품질이 도메인 문맥 없이 흔들릴 수 있음

대응:

- inventory/admin 중심 질문 템플릿을 먼저 만든다.
- 한국어 응답 규칙과 ERP 맥락 지시를 계속 보강한다.

### 리스크 4. RPA 외부 페이지 구조 변화에 취약할 수 있음

대응:

- selector 실패 로그 강화
- 스크린샷 보관
- 재시도와 실패 이력 확인 구조 유지

## 9. 결론

지금 시점에서 가장 좋은 다음 선택은 `새 기능을 넓게 벌리는 것`이 아니라, `대표 시나리오 1개를 정해서 운영 가능한 구조로 끝까지 연결하는 것`이다.

권장 시작점은 아래와 같다.

- `inventory` 대표 시나리오 확정
- `task history + callback 실패 logging` 구현
- `RPA 수집 결과 저장 + AI 요약` 연결

이 세 단계를 먼저 닫으면 그다음부터는 다른 도메인 확장도 훨씬 안정적으로 갈 수 있다.
