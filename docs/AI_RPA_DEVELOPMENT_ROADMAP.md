# DDUK ERP AI/RPA 단계별 로드맵

## 문서 목적

- 이 문서는 DDUK ERP 프로젝트에서 `RPA`, `이상 탐지`, `추천 발주`, `ERP 조회형 챗봇` 기능을 어떤 순서로 나눠서 붙일지 정리한 구현 로드맵이다.
- 목표는 한 번에 모든 대시보드를 완성하는 게 아니라, 현재 코드 기준으로 바로 구현 가능한 단계와 후속 계약이 필요한 단계를 분리하는 것이다.
- 이 문서는 구현 계획 문서이며, 실제 코드 반영 전에는 각 단계별 API, DB, UI 계약을 다시 고정한다.

> [!NOTE]
> - 현재 문서는 초안이 아니라 작업 기준 문서다.
> - 다만 회계 대시보드 RPA는 현재 범위에서 제외한다.
> - 회계 영역은 별도 요청이 생길 때 다시 계약을 열고 우선순위를 재조정한다.

## 기본 원칙

### 1. 대시보드에는 작은 위젯으로 붙인다

- 기존 대시보드 HTML과 페이지 JS를 크게 뒤엎지 않는다.
- `placeholder 1개 + helper JS 1개` 방식으로 붙인다.
- AI/RPA는 기존 CRUD를 대체하지 않고, API와 결과 위젯 형태의 보조 기능으로 붙인다.

예시:

```html
<div id="rpa-dashboard-widget" class="mt-6"></div>
<script src="../../services/admin/rpa-dashboard-helper.js"></script>
```

### 2. 공용 기반과 도메인 시나리오를 분리한다

- 먼저 `공용 trigger`, `task_history`, `callback`, `helper JS`, `결과 위젯`을 만든다.
- 그 다음에 구매, 재고, 인사 순으로 대시보드별 시나리오를 붙인다.
- 실제 도메인 데이터 자동 반영, 경고 자동 계산, 업무 규칙 연동은 뒤 단계로 분리한다.

### 3. 초반에는 조회형 시나리오 위주로 간다

- 1차 목표는 정보 `조회`, `수집`, `표시`까지다.
- 외부 사이트에 값을 입력하거나 ERP 데이터를 자동 수정하는 흐름은 후속 단계로 미룬다.

### 4. 사이드바 메뉴와 대시보드 위젯의 역할 분리
- **사이드바 메뉴**: AI 시스템의 대시보드 및 상세 옵션(임계값 설정, 수집 스케줄러 등)을 조율하는 **"관리자 전용 세팅 페이지"** 목적으로 남겨두어 독립적으로 운영합니다.
- **실제 대시보드**: 사용자가 실시간 업무 중에 바로 소비할 수 있는 **"핵심 요약 카드(위젯)"** 및 화면 우측 하단의 **"플로팅 AI 챗봇 위젯"** 형태로 배치하여 사용자의 업무 맥락(Context)을 끊김 없이 보조합니다.

## 현재 판단

- 현재 프로젝트는 `task_history`, `RPA callback`, `RPA client`, `관리자 모니터링 화면`이 일부 준비돼 있다.
- 하지만 `3개 taskType 공용 trigger`, `3개 시나리오 분기`, `대시보드별 mount 규칙`, `도메인 자동 반영 계약`은 아직 완성되지 않았다.
- 그래서 지금은 `공용 기반 -> 구매 -> 재고 -> 인사 -> 운영 보강` 순으로 작게 붙이는 게 맞다.

## 전체 우선순위

1. `Stage 0`: 공용 계약 정리
2. `Stage 1`: 공용 RPA 기반 1차 구현
3. `Stage 2`: 구매/발주 대시보드 1차 시나리오
4. `Stage 3`: 재고 대시보드 조회형 시나리오
5. `Stage 5`: 인사/급여 대시보드 조회형 시나리오
6. `Stage 6`: RPA 운영 UX 보강
7. `Phase 2`: 규칙 기반 이상 비용 탐지
8. `Phase 3`: 통계 기반 추천 발주
9. `Phase 4`: ERP 조회형 챗봇
10. `Phase 5`: ML/통계 고도화

> [!IMPORTANT]
> `Stage 4` 회계 대시보드 RPA는 현재 작업 계획에서 제외한다.
> 문서에는 기록만 남기고, 실제 구현 순서에는 포함하지 않는다.

## Stage 0. 공용 계약 정리

### 목표

- 3개 대시보드 시나리오를 엮는 공용 계약을 먼저 정리한다.
- 현재 코드에 없는 부분은 문서로 먼저 얼린다.

### 구현 작업

1. 공용 trigger API 요청 스키마 확정
2. `taskType`과 `actionName` 매핑 규칙 확정
3. callback payload 공통 필드 확정
4. helper JS가 인식할 페이지 경로와 mount 위치 확정
5. 결과 위젯 공통 UI 구조 확정

### 권장 계약

`POST /api/v1/admin/rpa/trigger`

```json
{
  "taskType": "PURCHASE_PRICE"
}
```

callback payload 예시:

```json
{
  "taskId": "rpa-task-001",
  "taskType": "PURCHASE_PRICE",
  "status": "success",
  "data": {},
  "error": null
}
```

### 완료 기준

- trigger 요청 필드가 고정된다
- `taskType -> actionName -> rpa script` 흐름이 문서로 정리된다
- 대시보드별 주입 경로가 확정된다

## Stage 1. 공용 RPA 기반 1차 구현

### 목표

- 3개 시나리오를 한 번에 만들지 않고, 공용 trigger 흐름과 공용 helper JS를 먼저 구현한다.

### 구현 작업

1. `frontend/services/admin/rpa-dashboard-helper.js` 생성
2. 현재 페이지 URL 기준으로 taskType을 분기하는 최소 로직 작성
3. 공용 trigger API 호출 로직 구현
4. 실행 중, 성공, 실패 상태를 보여주는 최소 위젯 구현
5. `task_history`에서 최근 1건 상태를 읽어 보여주는 간단한 상태 표시 연결

### 완료 기준

- 각 페이지에서 버튼 클릭 시 trigger 호출이 된다
- 성공/실패 상태가 화면에 보인다
- helper JS가 기존 페이지 로직을 과하게 건드리지 않는다

### 지금 단계에서 하지 않는 것

- 대시보드별 정교한 도메인 계산
- 외부 사이트에 데이터 쓰기
- 3개 시나리오 동시 완성

## Stage 2. 구매/발주 대시보드 1차 시나리오

### 목표

- 첫 실제 시나리오는 구매/발주 대시보드에서 시작한다.
- 현재 RPA 코드 구조와 가장 가깝고 시연 가치가 높다.

### 권장 시나리오

- 공급사 또는 단순 가격 페이지에서 기준 단가 정보를 수집한다
- 수집 결과를 발주 평균 단가와 비교해 대시보드에 보여준다

### 구현 작업

1. `PURCHASE_PRICE` taskType 추가
2. RPA 서버에서 구매 단가 수집 스크립트 연결
3. 구매/발주 대시보드에 버튼과 결과 위젯 주입
4. 수집 결과를 `최근 수집 단가`, `ERP 평균 단가`, `차이` 형태로 표시

### 완료 기준

- 구매/발주 대시보드에서 버튼 클릭 시 실제 RPA가 돈다
- 결과가 위젯으로 보인다
- `task_history`에 요청/성공/실패가 기록된다

### 아망티 기준 1차 실행 계약

- 1차 크롤링 대상 업체는 `아망티`로 고정한다.
- 초기 목적은 `가격/상품 정보 수집`으로 한정한다.
- 1차 수집 항목은 `품목명`, `가격`, `규격`, `재고 여부`, `상품 URL`, `수집 시각`으로 맞춘다.
- 수집 결과는 초반에 ERP 더미 데이터와 `비교/검증용`으로만 연결한다.
- `Stage 2` 범위에서는 수집 결과를 DB에 자동 반영하거나 자동 발주까지 연결하지 않는다.
- 첫 시연 범위는 아망티의 최소 1개 카테고리 또는 샘플 품목군 수집 성공과 구매/발주 대시보드 비교 표시까지로 잡는다.

### 아망티 연동 메모

- `PURCHASE_PRICE` taskType의 첫 실제 공급처 시나리오는 아망티 기준으로 설계한다.
- 품목 매핑은 초반에 완전 자동화하지 않고 ERP 더미 품목과 수동 확인 가능한 비교 카드 형태를 우선한다.
- 향후 업체가 늘어나더라도 `아망티 -> 추가 공급처` 순으로 확장하는 기준 업체 역할을 유지한다.

## Stage 3. 재고 대시보드 조회형 시나리오

### 목표

- 재고 대시보드에는 `부족/품절 조짐을 알려주는 조회형 시나리오`를 붙인다.

### 권장 시나리오

- 외부 공급사 사이트나 창고 페이지에서 재고/공급 제한 정보를 수집한다
- ERP 현재 재고 부족 품목과 나란히 보여주는 경고 위젯을 표시한다

### 구현 작업

1. `INVENTORY_SHORTAGE` taskType 추가
2. 재고 대시보드용 helper 분기 추가
3. 조회 결과를 경고 카드 형태로 표시

### 완료 기준

- 재고 대시보드에서 외부 조회 결과가 카드 형태로 보인다
- 내부 재고 부족 지표와 비교가 가능하다

### 지금 구현 가능성

- 부분 가능
- 초기 단계에서는 조회와 표시까지만 다루는 게 안전하다

## Stage 4. 회계 대시보드 조회형 시나리오

> [!IMPORTANT]
> 현재 RPA 작업 계획에서는 이 단계를 진행하지 않는다.
> 회계 대시보드 RPA는 이번 범위에서 제외하며, 별도 요청이 있을 때 다시 연다.

### 기록 목적

- 원래 후보는 `환율 수집형 시나리오`처럼 도메인 쓰기 없이 시연 가능한 항목이었다.
- 다만 현재 작업 범위에서는 구현하지 않고 보류 상태로만 남긴다.

## Stage 5. 인사/급여 대시보드 조회형 시나리오

### 목표

- 인사/급여 쪽도 처음부터 급여 계산 로직과 결합하지 말고, 외부 기준 정보 조회형으로 붙인다.

### 권장 시나리오

- 정부 또는 공공 사이트에서 최저임금/근태 가이드 정보를 수집한다
- 인사/급여 화면에 기준 정보 카드를 표시한다

### 구현 작업

1. `HR_MIN_WAGE` taskType 추가
2. 인사 또는 급여 대시보드 mount 위치 확정
3. 수집 결과를 기준 정보 카드로 표시

### 완료 기준

- 인사/급여 화면에서 버튼 클릭 후 기준 정보가 보인다
- 마지막 수집 시점이 표시된다

## Stage 6. RPA 운영 UX 보강

### 목표

- 앞 단계에서 붙인 RPA를 운영 가능한 수준으로 보강한다.

### 구현 작업

1. 최근 실행 이력 목록 UI 보강
2. 실패 메시지 정리
3. 재실행 버튼 추가
4. callback 지연 또는 누락 상태 표기 추가
5. 실행 중 상태 표현 추가

### 완료 기준

- 운영자가 실패 원인을 이해할 수 있다
- 재실행 흐름이 있다
- 현재 상태를 오해하지 않도록 문구가 정리된다

## Phase 2. 규칙 기반 이상 비용 탐지 MVP

### 목표

- 복잡한 ML보다 먼저 설명 가능한 규칙 기반 이상 탐지를 붙인다.

### 구현 작업

1. 규칙 기반 이상 탐지 로직 구현
2. 비용 데이터 배치 또는 주기 실행 구성
3. `anomaly_logs` 같은 저장 구조 설계
4. 관리자 경고 목록 UI 추가

### 운영 검토 상태

- `OPEN`
- `CONFIRMED`
- `FALSE_POSITIVE`
- `IGNORED`

## Phase 3. 통계 기반 추천 발주 MVP

### 목표

- 과거 재고 입출고와 주문 데이터를 바탕으로 설명 가능한 추천 발주 카드를 제공한다.

### fallback 규칙

- 최근 사용 이력이 부족하면 비활성화
- 현재고가 없으면 비활성화
- 리드타임 데이터가 없으면 비활성화
- 계산 결과가 비정상이면 `수동 검토 필요` 문구 표시

## Phase 4. ERP 조회형 AI 챗봇

### 목표

- 자유 대화형보다 먼저 실제 ERP 조회형 챗봇을 만든다.
- RAG보다 `내부 API 기반 조회 응답`을 우선한다.

### fallback 규칙

- 질문 의도가 불명확하면 일반 도움말 안내
- 대응 API가 없으면 지원하지 않는다고 안내
- 권한이 없으면 차단
- 응답 실패 시 재시도 안내

## Phase 5. ML/통계 고도화

### 목표

- 충분한 데이터가 쌓인 뒤 이상 탐지와 수요 예측 정확도를 높인다.

### 선행 조건

- 누적 이력 데이터 확보
- Phase 2, 3 운영 결과 확보
- 비교 가능한 검증 기준 확보

## 최종 권장 구현 순서

1. `Stage 0`에서 공용 계약부터 얼린다
2. `Stage 1`에서 공용 helper와 trigger 흐름을 만든다
3. `Stage 2` 구매/발주 대시보드부터 붙인다
4. `Stage 3` 재고 대시보드는 조회형까지만 붙인다
5. `Stage 5` 인사/급여 대시보드는 기준 정보 카드까지만 붙인다
6. `Stage 6`에서 운영 UX를 보강한다
7. 그 다음 `Phase 2`, `Phase 3`, `Phase 4`로 확장한다
8. `Phase 5` ML 고도화는 가장 뒤로 검토한다

## 최종 판단

- 현재 가장 건강한 경로는 `공용 기반 -> 구매 -> 재고 -> 인사 -> 운영 보강` 순으로 작게 붙이는 것이다.
- 회계 대시보드 RPA는 이번 범위에서 제외한다.
- 도메인 자동 반영과 업무 규칙 결합은 조회형 시연이 안정화된 뒤 별도 단계로 여는 게 맞다.

## 아망티 더미 데이터를 활용한 AI 예측/분석 연동 가이드

아망티 품목을 기준으로 적재할 더미 데이터가 단순한 정적 마스터 데이터에 머무르지 않고, **Phase 2(이상 비용 탐지)** 및 **Phase 3(추천 발주)** 등의 AI 모델이 정상적으로 학습하여 연산 결과를 반환할 수 있도록 데이터 생성 규격을 아래와 같이 설계합니다.

### 1. AI 추천 발주 및 수요 예측 (Phase 3)을 위한 재고 변동 이력
AI가 아망티 품목의 재고 소진 속도 및 적정 안전 재고를 예측할 수 있게 하기 위해, 다음 조건의 트랜잭션 데이터를 `stock_movements`와 `purchase_orders` 테이블에 쌓아야 합니다.
- **기간 및 주기**: 최소 3개월(권장 6개월)의 기간 동안, 주 1~2회 일정한 범위(예: 10~30개) 내에서 지속적으로 출고가 발생한 이력.
- **발주 리드타임 이력**: `purchase_orders` 테이블에 아망티 품목을 발주한 날짜와 실제 입고된 날짜의 차이가 평균 2~3일 정도로 일정하게 유지되는 발주 이력 최소 5건 이상 생성.

### 2. AI 이상 비용 탐지 (Phase 2)를 위한 Anomaly 데이터 설계
AI가 "평소와 다른 특이 거래"를 이상 탐지 모델(예: 임계값 및 통계 모델)로 짚어낼 수 있도록 정상 데이터 사이에 의도적인 노이즈 데이터를 심어둡니다.
- **정상 거래 이력**: 매월 아망티 거래처에 복리후생비 또는 소모품비 성격의 전표(`vouchers`)가 1~2회, 건당 100만 원~200만 원 수준으로 끊긴 이력.
- **이상 거래 (Anomaly) 시연 데이터**: 시연 시나리오의 타겟이 되는 날짜에 **갑자기 1,500만 원이 청구된 아망티 전표** 또는 **주말 새벽 시간대에 생성된 비정상적인 전표** 1~2건을 강제로 주입.

이와 같이 촘촘한 과거 변동 데이터를 SQL 형태로 생성하여 적재할 때 비로소 AI 대시보드 경고 위젯과 발주 추천 카드가 실감 나게 작동할 수 있습니다.
