# DDUK ERP AI/RPA 단계별 로드맵

## 문서 목적

- 이 문서는 DDUK ERP 프로젝트에 `RPA`, `이상 탐지`, `추천 발주`, `ERP 조회형 챗봇` 기능을 어떤 순서로 붙일지 정리한 구현용 로드맵이다.
- 특히 `4대 대시보드 완전체`를 한 번에 구현하는 대신, 현재 코드 기준으로 `당장 구현 가능한 단계`와 `후속 계약이 필요한 단계`를 나눠 적는다.
- 이 문서는 구현 계획 문서이며, 실제 코드 반영 전에는 각 단계별 API, DB, UI 계약을 태스크 단위로 다시 고정한다.

> [!NOTE]
> - 이 문서의 API 명세, DB 확장, 도메인 연계 규칙 중 일부는 초안이다.
> - 현재 레포 구조와 이미 존재하는 코드 기준으로 바로 가능한 범위를 우선 적고, 아직 없는 계약은 `후속 계약 필요`로 명시한다.
> - 멀티테넌트 전제는 두지 않는다.

## 기본 원칙

### 1. 비침습적 모듈러 방식 유지

- 기존 대시보드 HTML과 기존 도메인 JS를 대규모로 갈아엎지 않는다.
- 가능한 한 `placeholder 1개 + 독립 helper JS 1개` 방식으로 붙인다.
- 기존 도메인 CRUD와 업무 규칙은 그대로 두고, AI/RPA는 독립된 API 및 보조 위젯으로 연동한다.

예시:

```html
<div id="rpa-dashboard-widget" class="mt-6"></div>
<script src="../../services/admin/rpa-dashboard-helper.js"></script>
```

### 2. 공용 기반과 도메인 연계를 분리

- 먼저 `공용 trigger`, `task_history`, `callback`, `helper JS`, `결과 위젯`을 만든다.
- 그 다음에 구매, 재고, 회계, 인사 순으로 대시보드별 시나리오를 붙인다.
- 실제 도메인 데이터 자동 반영, 경고 자동 계산, 업무 규칙 연동은 뒤 단계로 분리한다.

### 3. 조회형 먼저, 쓰기형은 나중

- 1차는 외부 정보 `조회`, `수집`, `표시`까지만 한다.
- 외부 사이트에 `등록`, `전송`, `대량 입력` 같은 쓰기형 자동화는 후속 단계로 미룬다.

## 현재 판단

- 현재 프로젝트는 `task_history`, `RPA callback`, `RPA client`, `관리자 모니터링 화면`이 일부 준비돼 있다.
- 하지만 `4개 taskType 공용 trigger`, `4개 시나리오 분기`, `대시보드별 mount 규칙`, `도메인 자동 반영 계약`은 아직 완성되지 않았다.
- 그래서 `4대 대시보드 완전체`는 한 단계 목표로 두되, 실제 구현은 더 작은 단계로 쪼개는 게 맞다.

## Stage 0. 공용 계약 정리

### 목표

- `4대 대시보드 완전체`에 앞서 공용 기반 계약부터 정리한다.
- 현재 코드에 없는 부분을 먼저 문서상으로 얼린다.

### 구현 작업

1. 공용 trigger API 요청 스키마 확정
2. `taskType`과 `actionName` 매핑 규칙 확정
3. callback payload 공통 필드 확정
4. helper JS가 인식할 페이지 경로와 mount 위치 확정
5. 결과 위젯 공통 UI 구조 확정

### 권장 계약

`POST /api/v1/admin/rpa/trigger`

```json
{
  "taskType": "PURCHASE_PRICE"
}
```

callback payload 예시:

```json
{
  "taskId": "rpa-task-001",
  "taskType": "PURCHASE_PRICE",
  "status": "success",
  "data": {},
  "error": null
}
```

### 완료 기준

- trigger 요청 필드가 고정된다
- `taskType -> actionName -> rpa script` 흐름이 문서로 정리된다
- 주입 대상 대시보드 경로가 확정된다

### 지금 구현 가능한 부분

- 가능
- 현재 `RpaClientService`, `task_history`, `callback controller`가 이미 있어서 그 위에 계약을 얹기 좋다

### 후속 계약 필요

- 실제 대시보드 경로 통일
- callback에 `taskType`을 넣을지 `actionName`만 유지할지 확정

## Stage 1. 공용 RPA 기반 1차 구현

### 목표

- 4개 시나리오를 한 번에 만들지 않고, 공용 trigger 흐름과 공용 helper JS를 먼저 구현한다.

### 구현 작업

1. `frontend/services/admin/rpa-dashboard-helper.js` 생성
2. 현재 페이지 URL 기준으로 taskType을 분기하는 최소 로직 작성
3. 공용 trigger API 호출 로직 구현
4. 실행 중, 성공, 실패 상태를 보여주는 최소 위젯 구현
5. task_history의 최근 1건 상태를 읽어 보여주는 간단한 상태 표시 연결

### 완료 기준

- 한 페이지에서 버튼 클릭 시 trigger 호출이 된다
- 성공/실패 상태가 화면에 보인다
- helper JS가 기존 도메인 로직을 크게 건드리지 않는다

### 지금 구현 가능한 부분

- 가능
- 특히 관리자/구매/회계 대시보드부터는 붙이기 쉽다

### 지금 단계에서 하지 않는 것

- 대시보드별 정교한 도메인 계산
- 외부 사이트에 데이터 쓰기
- 4개 시나리오 동시 지원 완성

## Stage 2. 구매/발주 대시보드 1차 시나리오

### 목표

- 첫 실제 시나리오는 구매/발주 대시보드에서 시작한다.
- 현재 레포 구조상 가장 현실적인 첫 시연 대상이다.

### 권장 시나리오

- 공공 또는 단순 웹 페이지에서 기준 단가 정보 수집
- 수집 결과를 발주 평균 단가와 나란히 비교 표시

### 구현 작업

1. `PURCHASE_PRICE` taskType 추가
2. RPA 서버에서 구매 단가 수집 스크립트 연결
3. 구매/발주 대시보드에 버튼과 결과 위젯 주입
4. 수집 결과를 `최근 수집 단가`, `ERP 평균 단가`, `차이` 형태로 표시

### 완료 기준

- 구매/발주 대시보드에서 버튼 클릭 후 실제 RPA가 돈다
- 결과가 위젯에 보인다
- task_history에 요청/성공/실패가 기록된다

### 지금 구현 가능한 부분

- 가능
- 현재 RPA 코드가 구매 관련 작업 흐름에 가장 가까워서 첫 단계로 적합하다

### 보류할 부분

- 자동 발주 반영
- 거래처 사이트 로그인형 등록 작업

## Stage 3. 재고 대시보드 조회형 시나리오

### 목표

- 재고 대시보드에는 `부족 위험을 알려주는 조회형 시나리오`를 붙인다.

### 권장 시나리오

- 외부 공급 사이트나 참고 페이지에서 품절/공급 제한 정보 수집
- ERP 현재 재고 부족 품목과 나란히 보여주는 경고 위젯 표시

### 구현 작업

1. `INVENTORY_SHORTAGE` taskType 추가
2. 재고 대시보드용 helper 분기 추가
3. 조회 결과를 경고 카드로 표시

### 완료 기준

- 재고 대시보드에서 외부 조회 결과가 카드 형태로 보인다
- 내부 재고 부족 지표와 나란히 비교 가능하다

### 지금 구현 가능한 부분

- 부분 가능
- 외부 조회와 표시까지는 가능

### 후속 계약 필요

- `안전 재고 보충 연동`
- 실제 발주 생성 연계
- 공급 제한 상태를 내부 재고 정책과 자동 연결하는 규칙

## Stage 4. 회계 대시보드 조회형 시나리오

### 목표

- 회계 대시보드는 `환율 수집형 시나리오`처럼 도메인 쓰기 없이 시연 가능한 항목부터 붙인다.

### 권장 시나리오

- 공공 또는 단순 환율 페이지에서 USD, EUR, JPY 기준 환율 수집
- 회계 대시보드 위젯에 오늘 환율 요약 표시

### 구현 작업

1. `ACCOUNTING_EXCHANGE` taskType 추가
2. 회계 대시보드 mount 위치 확정
3. 환율 조회 결과 카드 및 마지막 갱신 시간 표시

### 완료 기준

- 회계 대시보드에서 버튼 클릭 후 환율 정보가 표시된다
- 최근 환율 수집 시간이 보인다

### 지금 구현 가능한 부분

- 가능
- 조회형 시나리오라서 업무 규칙 충돌이 적다

### 후속 계약 필요

- 외화 전표 원화 환산 자동 반영
- 외상 대금 실시간 환산 로직 연계

## Stage 5. 인사/급여 대시보드 조회형 시나리오

### 구현 작업

1. `HR_MIN_WAGE` taskType 추가
2. 인사 또는 급여 대시보드의 mount 위치 확정
3. 수집 결과를 기준 정보 카드로 표시

### 완료 기준

- 인사/급여 화면에서 버튼 클릭 후 기준 정보가 보인다
- 마지막 수집 시점이 표시된다

### 지금 구현 가능한 부분

- 부분 가능
- 기준 정보 조회와 표시까지는 가능

### 후속 계약 필요

- `최저임금 미달 의심 직원 자동 매칭`
- 실제 급여 대장 경고 연동
- 인사 정책과 회계 연동 판단 규칙

## `4대 대시보드 완전체`의 재정의

기존 문서에서 말하던 `4대 대시보드 완전체`는 이제 한 단계 목표가 아니라 아래 3층으로 본다.

1. `1층: 공용 기반`
   - trigger
   - callback
   - helper JS
   - task_history
   - 결과 위젯

2. `2층: 대시보드별 조회형 시나리오`
   - 구매 단가
   - 재고 부족 참고 정보
   - 환율
   - 최저임금/노무 가이드

3. `3층: 도메인 연계형 고도화`
   - 자동 경고
   - 내부 정책 계산
   - 발주/전표/급여 로직 반영

즉 `완전체`는 최종 상태로 두고, 실제 구현은 `1층 -> 2층 -> 3층` 순서로 간다.

## Phase 2. 규칙 기반 이상 비용 탐지 MVP

### 목표

- 복잡한 ML보다 먼저 설명 가능한 규칙 기반 이상 탐지를 붙인다.
- 사람에게 알려주는 경고 시스템이 목표지, 자동 차단이 목표는 아니다.

### 구현 작업

1. 규칙 기반 이상 탐지 로직 구현
2. 비용 데이터 배치 또는 주기 실행 구성
3. `anomaly_logs` 같은 저장 구조 설계
4. 관리자 경고 목록 UI 추가

### 운영 검토 플로우

- 상태값 예시:
  - `OPEN`
  - `CONFIRMED`
  - `FALSE_POSITIVE`
  - `IGNORED`

### 지금 구현 가능한 부분

- 가능

## Phase 3. 통계 기반 추천 발주 MVP

### 목표

- 과거 재고 입출고 데이터를 기반으로 설명 가능한 추천 발주 카드를 제공한다.

### 구현 작업

1. 재고 이력 집계 API 구성
2. 평균 사용량, 안전재고, 리드타임 기반 계산
3. 추천 카드 UI 추가
4. 발주서 작성 화면 이동 연결

### fallback / disable 규칙

- 최근 사용 이력이 부족하면 숨김
- 현재고가 없으면 숨김
- 리드타임이 없으면 비활성화
- 계산 결과가 비정상이면 `수동 검토 필요` 표시

### 지금 구현 가능한 부분

- 가능

## 최종 권장 구현 순서

1. `Stage 0`에서 공용 계약부터 얼린다
2. `Stage 1`에서 공용 helper와 trigger 흐름을 만든다
3. `Stage 2` 구매/발주 대시보드부터 붙인다
4. `Stage 4` 회계 대시보드를 다음 시연 대상으로 붙인다
5. `Stage 3` 재고 대시보드는 조회형까지만 붙인다
6. `Stage 5` 인사/급여 대시보드는 기준 정보 카드까지만 붙인다
7. `Stage 6`에서 운영 UX를 다듬는다
8. 그 다음 `Phase 2`, `Phase 3`, `Phase 4`로 확장한다
9. `Phase 5` ML 고도화는 가장 나중에 검토한다

## 최종 판단

- `4대 대시보드 완전체`는 구현 불가능한 목표는 아니다.
- 다만 지금 프로젝트에선 그것을 `첫 단계`로 보면 과하다.
- 현재 가장 건강한 경로는 `공용 기반 -> 구매 -> 회계 -> 재고 -> 인사 -> 운영 보강` 순으로 작게 붙이는 것이다.
- 도메인 자동 반영과 업무 규칙 결합은 조회형 시연이 안정화된 뒤에 별도 단계로 여는 것이 맞다.
